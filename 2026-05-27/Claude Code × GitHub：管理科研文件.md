> 这篇聊GitHub。不是让你学git命令，而是聊为什么科研工作者需要版本控制，以及配合Claude Code之后，这件事变得有多简单。

# 一、你有没有这样的文件夹

先说一个场景，做过科研的人大概都不陌生。你打开论文项目的文件夹，里面是这样的：

```
终稿.docx
终稿_v1.docx
终稿_v2.docx
终稿_v2_导师批注.docx
终稿_v3_改_最终版.docx
终稿_v3_改_最终版_真的最终.docx
终稿_v3_改_最终版_真的最终_20260518.docx
```

发给合作者之前，你要想半天：这个文件是最新的吗？上周导师改的那版在哪？那个删掉的段落能找回来吗？

如果是代码文件，情况更严重。Stata的do文件改了十几版，某个稳健性检验用了哪套控制变量，三个月后自己都不记得了。审稿人回来问"你们子样本是怎么界定的"，你得重新跑一遍，祈祷结果还能对上。

这不是个人习惯不好。这是在没有版本控制工具的情况下，做多稿迭代工作的必然结果。每个人都在用文件名充当版本号，用备份文件夹充当历史记录，用记忆充当变更日志——而这三件事，都是靠不住的。

# 二、科研有一个正在变严重的问题：可复现性

这个问题不只是个人效率问题，它背后有一个更大的背景。

过去十年，学术界对研究可复现性（reproducibility）的要求越来越高。​顶刊开始要求提交数据和代码；Nature、Science系列期刊已经在系统性地推行代码公开政策；AEA的政策要求所有接受发表的实证论文提交可复现的数据和代码包（replication package）；现在国内很多核心期刊也陆续要求作者公布可复现的数据和代码包（例如，最早开始的中工，最近的经济研究、管理世界、经济学季刊、世界经济等）。​这件事从“加分项”变成了“必要条件”，速度很快。

背后的逻辑很直接：如果一项研究无法被独立复现，它的可信度就存疑。而实现可复现性的前提，是研究过程有完整的记录——数据从哪里来、经过哪些清洗步骤、回归用了哪些控制变量、哪些结果是最终版、哪些是中途放弃的路径。

没有版本控制工具，这些记录几乎不可能系统地维护。

Git和GitHub解决的正是这个问题。现在简单介绍一下这两个到底是什么？具体地，Git是一个版本控制系统，记录每一次文件的变更；GitHub是托管平台，让这些记录可以在云端保存和共享。这两个工具在工程师圈子里已经是基础配置，但在社科研究者里，使用率还远没有到该有的水平——原因主要是学习门槛：git命令多、出错难排查、跟已有工作流接入不顺畅。

这个局面，从Claude Code的出现便正在改变。

# 三、三个科研场景，git 都有直接答案

-   ## 场景一：多人协作
    

传统方式的多人协作是这样运转的：A写完一部分，用邮件或微信发给B，B改完发回来，中间如果A又动了一版，两人的修改就会打架，最后不知道以哪个为准。这个问题随着合作者人数的增加会指数级恶化。

GitHub的解决思路是branch（分支）：每个人在自己的分支上独立工作，主干版本不受影响；完成之后提交合并（merge），系统自动整合双方的修改；如果两人改了同一个地方，系统会明确标出冲突，逐一处理，而不是悄悄覆盖。

具体到科研写作：

-   论文第一章由A负责，第三章由B负责，各自开一个branch同步推进，不需要互相等待；
    
-   导师的批注意见单独提交为一个commit，标注「导师第一轮意见」，永久留存，不会和作者的修改混在一起；
    
-   合作者在境外、时差大，不再需要约时间同步——每个人在自己的节奏里工作，合并时系统处理。
    

即便是一个人做的项目，分支管理也有用。想试一个新的识别策略，但不想破坏已经稳定的主版本——开一个新branch试验，试验失败直接丢弃，主干不受任何影响。试错成本接近于零。

邀请合作者也很简单：进入仓库页面，点击Settings → Collaborators → Add people，输入对方的GitHub用户名发出邀请，对方接受后就能访问和编辑这个私有仓库。权限可以细分——只读（只能看）、写入（可以推送）或管理员——根据合作深度自行设定。

-   ## 场景二：留痕与可复现
    

做过实证研究的人都知道，论文从开始到投稿，代码会经历几十次甚至上百次修改。最终版本和第一版之间，变量选择、样本界定、标准误处理、固定效应设置——每一个环节都可能改过好几次。

git的commit记录，就是这个过程的完整日志。

每次执行一次commit，会留下三件事：时间戳（什么时候改的）、改动内容（哪些行新增、哪些行删除、哪些行修改）、提交说明（这次改动的理由）。这个记录不需要手动维护，它是git工作方式的自然产物。

以Stata的do文件为例，一段真实的commit历史可能是这样的：

```
commit  基准回归初版，控制变量：规模、年龄、所有制性质
commit  加入行业×年份固定效应，系数发生变动
commit  删除异常值（双端 winsorize 1%），回归结果基本稳健
commit  加入子样本检验，系数符号不变、量级略小
commit  按所有制分组回归，异质性分析部分
commit  根据审稿人意见：补充PSM匹配稳健性检验
```

六个月后投稿，审稿人问「你们样本删失的标准是什么」——打开commit记录，精确到哪次、改了哪行、为什么改。这不是靠记忆，也不是靠另存的"修改说明.txt"，而是工作流的一部分，自动沉淀下来的档案。

这就是可复现性真正落地的方式：不是事后整理，而是过程中的自然记录。

找回历史版本是git另一个经常被低估的能力。有时候改了一个方向，改着改着发现原来的思路更好——在没有版本控制的情况下，这意味着一切从头来过，或者翻找备份文件。有了git，你可以让Claude Code：

```
帮我回到三周前那个版本看一下，那时候稳健性检验的写法
```

它会找到对应的commit，还原那个时间点的文件状态，你看完再决定要不要把那段内容移植回来。历史不会消失，只是被归档了。

-   ## 场景三：文件结构与长期管理
    

一个论文项目的文件，分散在桌面、下载文件夹、云盘、邮件附件里——这几乎是科研工作者的常态。GitHub仓库解决的不只是版本控制，还是整个项目的文件组织。

一个标准的实证项目仓库结构可以是：

```
research-project/
├── data/
│   ├── raw/           # 原始数据，只读，不修改
│   └── clean/         # 清洗后数据
├── code/
│   ├── 00_setup.do    # 路径和全局宏
│   ├── 01_clean.do    # 数据清洗
│   ├── 02_main.do     # 主回归
│   └── 03_robust.do   # 稳健性检验
├── output/
│   ├── tables/        # 回归结果表格
│   └── figures/       # 图
└── paper/
└── main.tex       # 论文正文
```

这个结构在GitHub网页上一目了然。更重要的是，这个仓库本身就是论文最完整的档案：从数据清洗的第一步，到最终投出去的版本，每一个中间状态都有记录，任何一个节点都可以精确还原。

当期刊要求提交replication package，你需要做的不是临时整理，而是把这个仓库链接发过去。

# 四、配置方法：Claude Code + GitHub，不需要记命令

过去，git的学习门槛让很多研究者望而却步。命令多、报错难理解、操作失误风险高——这些问题是真实存在的，不是借口。

现在的情况不一样了。配合Claude Code，整个git工作流可以用自然语言驱动。你不需要记任何命令，Claude Code作为执行层，你作为决策层——你告诉它要做什么，它告诉你它打算怎么做，你确认，它执行。

-   第一步：注册 GitHub 账号
    

前往github.com注册，用邮箱注册即可，免费账号完全够用。

注册完成后，点击右上角+→New repository新建仓库：

-   Repository name：仓库名称，建议英文，比如research-project或paper-2024
    
-   Visibility：选Private
    

为什么建议Private？科研数据通常涉及敏感信息或数据使用协议限制，Private仓库只有你授权的人可以访问。等论文投稿或发表后，如果需要公开replication package，再切换成 Public——一个选项的事。

-   第二步：安装GitHub CLI
    

GitHub CLI是让终端和GitHub通信的工具，Claude Code通过它执行推送和仓库操作。

Mac：

```
brew install gh
```

Windows：

```
winget install GitHub.cli
```

安装完成后运行gh --version，看到版本号说明成功。

-   第三步：授权登录
    

```
gh auth login
```

按提示选择：

1.  Where do you use GitHub? → GitHub.com
    
2.  What is your preferred protocol? → HTTPS（推荐，不需要配置SSH密钥）
    
3.  How would you like to authenticate? → Login with a web browser
    

浏览器弹出授权页，输入终端显示的验证码，点击授权，完成。整个过程两分钟以内。

-   第四步：初始化并推送
    

打开Claude Code，进入你的项目目录，直接说：

```
帮我把这个项目初始化git，创建第一次提交，然后推送到一个新的私有GitHub仓库
```

Claude Code会依次执行git init、git add、git commit、gh repo create --private --push。每一步它都会显示要执行的命令请求你确认，你点Yes，它执行。完成后打开GitHub网页，所有文件已经在上面了。

-   第五步：设置.gitignore，避免追踪不必要的文件
    

这一步很多人会跳过，但值得花两分钟做。.gitignore是一个配置文件，告诉git哪些文件不需要追踪。

科研项目里通常不需要追踪的文件：

-   原始数据文件（.dta、.csv）：原始数据体积大，而且通常有数据使用限制，不适合上传到云端。数据路径和清洗逻辑记录在代码里就够了。
    
-   LaTeX编译产生的辅助文件（.aux、.log、.synctex.gz）：这些是编译时自动生成的，不需要版本追踪。
    
-   系统文件（.DS\_Store等）：Mac系统自动生成，和研究内容无关。
    
-   大体积输出文件：中间产物的PDF、临时图片等，如果可以从代码重新生成，就没必要追踪。
    

让Claude Code帮你生成：

```
帮我创建一个.gitignore 文件，项目是Stata + LaTeX，排除原始数据、编译辅助文件和系统文件
```

它会生成一个合适的.gitignore，确认后加入仓库。后续这些文件就不会出现在待提交列表里，不用每次手动排除。

# 五、日常工作流：告诉Claude Code，它处理git

配置完成后，日常使用只有一件事：做完一个阶段，告诉Claude Code提交一下。

比如跑完主回归：

```
帮我提交一下，说明是主回归初版，双向固定效应，聚类标准误到企业层面
```

Claude Code会生成一条commit信息，让你确认，然后执行git add+git commit+git push，文件自动同步到GitHub。

比如导师改完稿回来：

```
帮我提交这一版，说明是根据导师第二轮意见修改，主要调整了机制分析部分
```

比如想找回两周前的某段分析：

```
帮我看一下两周前那个版本的稳健性检验部分，我想比较一下和现在的差别
```

整个流程你不需要记任何git命令。commit记录会自动沉淀下去，六个月后、一年后，每一次改动都有迹可查。

# 六、不只是Claude Code：这套工作流是平台无关的

这里值得多说一句。GitHub上的仓库、commit历史、文件结构——这些东西不属于Claude Code，它们属于你。任何支持git的工具都可以接入同一个仓库，继续在同一套记录上工作。

OpenAI的Codex同样如此。Codex本质上是另一个AI编程助手，它读取你的代码、帮你修改、执行git操作——和Claude Code的工作方式几乎是平行的。如果你的项目已经在GitHub上，切换到Codex使用的成本几乎为零：打开同一个仓库，继续提交commit，历史记录完整保留，工作流不需要重新建立。

这一点在当前的AI工具格局下尤其值得注意。各家平台的账号策略、访问限制随时可能变化，但你的GitHub仓库和commit历史不会因为平台的变动而消失。把研究过程沉淀在GitHub上，实际上是在给自己的工作做一个平台无关的备份——不管以后用哪个AI工具接手，档案在那里，可以无缝继续。

从这个角度看，配置GitHub的价值不只是「让当前的Claude Code用起来更顺」，而是在给自己的研究工作建立一个长期可靠的基础设施。这件事越早做越好。

# 七、一句话总结

GitHub不是程序员专属的工具。对科研工作者来说，它是版本记录 + 协作平台 + 项目档案库三合一的基础设施。以前这套东西学起来有门槛，所以大多数人选择了将就——用文件名命名版本，用记忆代替日志，用邮件传文件做协作。

现在有了Claude Code 或Codex，这个门槛几乎消失了。你需要做的只是告诉它你想要什么，它处理所有的git操作，你只负责确认。

把GitHub配置好，是把研究过程变成可追溯档案的第一步。这件事值得花半个小时做一次。
